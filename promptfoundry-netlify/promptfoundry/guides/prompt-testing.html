How to test your own prompts (without building a lab)

You do not need infrastructure to know whether a prompt works. You need ten runs, a fixed rubric and the discipline to write down the failures.

Most prompt quality is guesswork dressed up as intuition. You try a prompt, the output is good, you save it. Three weeks later it is mediocre and you cannot tell whether the prompt changed, the model changed, or you are remembering one lucky sample. A small test habit fixes that.

Step 1 — Freeze the inputs

Write down the exact inputs you will use, and use the same ones every run. If the prompt has variables, fill them once with realistic values and save that filled version. Otherwise you are testing the input, not the prompt.

Step 2 — Run it ten times

Ten runs, fresh context each time, default settings. Ten is enough to separate "usually works" from "worked once" without becoming a research project. Keep all ten outputs — the failures are the useful part.

Step 3 — Score against four criteria

CriterionQuestionPoints
UsableCould you ship this with minor edits?15
On formatDid it respect the length, structure and output type?10
Fact-safeAny invented numbers, sources or quotes? Assumptions labelled?10
On voiceDoes it sound like the brief — or like generic model-speak?5

Score each run out of 40. A prompt that averages above 34 is ready. Below 28, something structural is missing — usually context, format or constraints. Between the two, it works for internal drafts but not customer-facing work.

Step 4 — Write down the misses

For every failed run, note the failure mode in five words or fewer: invented a statistic, ignored the word limit, sounded like a press release. Patterns appear after a handful of runs, and patterns tell you which line of the prompt to fix. One failed run is noise; the same failure four times is a design flaw.

Step 5 — Re-test when the model changes

This is the step almost everyone skips. Prompts are coupled to model behaviour: instruction-following, refusal thresholds and default verbosity all shift between releases. Keep a test date and the model version with every prompt. When a new version ships, re-run your ten. If the pass rate drops, the prompt needs work — not a screenshot from launch week.

A useful habit: store prompts as files with a header — model version, last tested date, pass rate, known failure modes. The header is what turns a prompt collection into a test log. Ours looks like the metadata block on every prompt in the library.

The folder structure that actually works

prompts/
  cold-email/
    prompt.md        # the template, with [VARIABLES]
    inputs.md        # the frozen filled inputs
    results/
      2026-10-12-gpt-6.1.md   # ten outputs, scored
      2026-10-12-sonnet-5.5.md
    notes.md         # failure modes, fixes tried

That is the whole system. No dashboard, no tooling — just the ability to answer "when did you last check this, and what broke?"

Copy the template

# [PROMPT TITLE]

Model: [MODEL + VERSION]
Last tested: [YYYY-MM-DD]
Pass rate: [X/10]
Known failures: [FAILURE MODE 1], [FAILURE MODE 2]

---

[PROMPT TEMPLATE WITH [VARIABLES]]

Three lines of metadata turn a prompt into something you can trust — and re-test. If you would rather not do it manually, every prompt on this site ships with its metadata in the drawer, and the Studio can export a prompt as a Markdown file with the header included.

When testing is overkill

For one-off tasks, run it twice and move on. The protocol earns its keep when a prompt is used weekly, shared with a team, or embedded in a product. That is also the moment a prompt stops being a prompt and becomes infrastructure — and infrastructure deserves a test date.
